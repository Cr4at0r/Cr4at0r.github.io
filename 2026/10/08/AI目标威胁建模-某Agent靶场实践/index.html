AI 目标威胁建模：某 Agent 靶场实践

发表于2026-10-08|更新于2026-10-13|AI安全研究
|浏览量:

这是一次某 Agent 靶场实践的复盘。靶场代号 AgentRange-01，模拟的是一个金融场景里的「智能财富助理」：用户通过聊天入口查产品、看行情、读研究报告，Agent 背后接了 RAG、工具调用、风控和内部服务。靶场不是真实客户项目，所有域名、IP、模型名和产品名都只存在于隔离环境里。

这次实践给出的条件很有限：没有完整架构图，没有代码仓库，只有对外聊天入口、一个 UAT 入口、少量脱敏情报和一份演练授权。目标是回答三个问题：这个 Agent 系统里有哪些边界？哪些边界能被组合成攻击路径？如果要修，控制点应该放在哪里？

所以这篇不写「先了解业务、再识别资产、最后评估风险」这种空转流程，而是把威胁建模拆成可执行动作：把零散情报压成架构图，用低频探测确认防护，把攻击面映射成候选路径，再决定先测哪里、停在哪里、怎么写报告。

0. 靶场背景

1. 业务设定

AgentRange-01 模拟一家金融机构对外提供的财富助理 Agent。用户可以问基金净值、查看资产配置建议、检索研究报告。系统对外只暴露一个自然语言入口，但内部按企业 AI 应用常见方式拆成多个组件：

靶场刻意保留了几类企业环境里很常见的弱点形态：UAT 和生产可能共享数据；风控只覆盖显式提示注入；工具层参数缺少强校验；RAG 返回的元数据过细；向量库被认为只在内网所以不做鉴权。 这些不是漏洞清单，而是需要红队用证据确认的假设。

2. 起点条件

演练开始时只有四类材料：

材料 内容 限制
授权范围 只能访问 agentrange.lab 内的靶场资产 禁止访问真实外网系统
对外入口 wealth-assistant 和 chat-uat 不提供账号，UAT 需要自行确认认证面
脱敏情报 架构注释、依赖片段、聊天样例 信息可能过期、不完整，甚至互相矛盾
演练目标 验证信息泄露、RAG 枚举、工具滥用和跨环境影响 禁止破坏服务、批量删除数据和留下持久化后门

我把成功标准分成四层：

  1. 识别层：确认模型、RAG、Agent 工具和风控的存在。
  2. 暴露层：判断哪些字段、参数和返回值把内部信息带到了用户边界。
  3. 路径层：找到至少一条从公开对话入口到达内部数据或工具能力的组合路径。
  4. 防御层：指出每个关键动作应该在哪里校验、审计和阻断。

换句话说，靶场不是比谁会堆注入词，而是比谁能把一套复杂 Agent 系统的攻击计划讲清楚。

1. 先把交付物定死

威胁建模最容易变成两页「AI 存在风险」的综述。开工前先把交付物固定下来，后面每个动作都服务于其中一项：

产出物 回答的问题 反例
目标卡 测什么、不测什么、业务影响是什么 只写「测试 AI 助手」，不写权限和数据边界
证据台账 每个推断来自哪里、置信度多高 把旧注释当成当前架构事实
攻击面矩阵 每个组件暴露哪些能力，谁在边界上 只列模型/RAG/Agent，不写输入来源和输出去向
信任边界图 数据在哪几个点跨过权限边界 只画服务拓扑，不画文档、提示词和工具结果
候选路径树 哪些入口能组合出业务影响 只报单点越狱，不说能不能到数据或工具
执行计划 每步的验证信号、预算和止损条件 直接循环跑注入词，直到触发封禁
防御清单 修复放在哪个控制点 只给「加强提示词过滤」这种不可验证建议

这七张表比漏洞数量重要。漏洞只是执行阶段的产物，威胁模型的价值是告诉你为什么先测这里、不测那里，以及一条路径失败时怎么切换。

2. 侦察重建架构：第一小时不碰目标

这个阶段的目标不是找漏洞，而是画一张「系统长什么样」的草稿图，给后面的主动探测定坐标。我不急着发请求，先把靶场给到的静态信息和可公开访问的说明读完。

1. 入口与命名特征

靶场内部的三个主机名已经能说明很多问题：

主机名 初步推断 记录动作
wealth-assistant.agentrange.lab 生产模拟入口，主目标 记录响应头、限流和基础行为
chat-uat.agentrange.lab UAT 入口，安全基线可能更弱 标记为候选入口，暂不登录
llm-gw.agentrange.lab LLM 统一网关 后面可能存在多模型路由
emb-api.agentrange.lab 向量化服务 RAG 链路存在的直接证据

chat-uat 这个名字当时没有立刻引起注意，但它后来成了整条路径里的关键边。第一小时不要做筛选，所有看起来无关的线索都进证据台账。 你不知道哪一条以后会连成攻击路径。

2. 依赖片段和架构注释

脱敏情报里有几句零散注释，信息密度很高：

这些线索能推出四个方向：

线索 初步推断 影响的计划
FinLLM-13B 不是公有大模型直连 模型窃取优先级降低，应用层优先级升高
LangChain 0.1.x 应用框架较旧 关注工具调用模板和已知组件行为
Milvus 存在向量库 嵌入向量还原和知识库枚举进入候选路径

注意，这只是 C 级推断。注释可能来自旧版本，也可能和现网配置不一致，所以它先写成「疑似组件」，不写成事实。

3. HTTP 头、错误信息和限流参数

对主入口做一次最小探测，看服务端自己会说什么：

这里能抽出三个计划参数：

  1. X-Backend-Pool 暴露后端池命名，多模型或多实例架构基本确认。
  2. X-Ratelimit-Limit: 20 说明每分钟只有 20 次交互预算，后续所有探测必须节流。
  3. 错误页保持统一文案，说明前端网关做了基础规范化，但异常分支还要另测。

限流不是一个普通响应头，它决定测试节奏。一百轮粗暴注入和十轮精准探测，在靶场风控和安全评审里是完全不同的两个事件。

3. 运行时指纹：让目标自己交底

被动收集解决「系统大概是什么」，运行时指纹解决「防护开没开、数据流通不通」。我不做全量注入，先按 20/min 的限流节奏分三轮跑七个探测：

# 探测 结果 推断

第 4 条的完整响应是整次实践里信息量最大的一次交互：

这段响应说明三件事：title 暴露知识库内容主题；path 暴露目录结构和上传组织；score 暴露相似度阈值。攻击者不需要拿到数据库，只要反复改写提问，就能用 score 反推检索行为，甚至逐步枚举高价值文档。

1. 防护也要建模

风控不是「能拦/不能拦」这种二值对象。它的实现层决定你后面选哪条路径：

防护层 常见表现 对攻击计划的影响
输入关键词层 拦「ignore previous」「system prompt」 换成正常业务语义，不硬碰
模型策略层 拒答但不触发全局告警 需要控制次数，避免形成模式
上下文组装层 对拼接结果做规范化 关注模板变量、引用块和分隔符
工具层 校验参数、权限和目标地址 真正的控制点，必须单独测
审计层 只记输入/输出，不记工具参数 防御盲区，报告里要指出

这个靶场在第 3、6 条里表现出关键词层特征，而不是工具层防护。所以后面不能继续堆注入词，要顺着 Agent 的正常职责找带参数的合法动作。

4. 攻击面映射与信任区域划分

架构确认后，把攻击面全景对着靶场目标过一遍。这里不是抄一张通用清单，而是把每个组件放回「输入来源、能力、输出去向」里看。

1. 组件 × 攻击面矩阵

组件 确认状态 对应攻击面 边界问题 优先级
FinLLM-13B 指纹确认 越狱、行为诱导、模型窃取 输出是否会被当成指令/工具参数 中
Sentinel-Guard 拦截行为确认 防护绕过 只覆盖哪些输入字段和会话状态 中
RAG + Milvus sources 泄漏确认 知识库枚举、投毒、嵌入还原 谁能写入，检索结果是否当指令 高
Agent + quote-tool 工具调用确认 工具滥用、参数注入、SSRF 参数是否校验，返回值是否二次拼上下文 最高
LLM 网关 HTTP 头推断 路由操纵、配额绕过 是否跨环境共享路由和密钥 中
knowledge-admin 架构注释确认 文档上传投毒 上传、解析、切片、入库是否同权 高
K8s/容器平台 未确认 SSRF、凭证访问、容器逃逸 出站请求能否触达内部元数据 备选

这张表里的优先级不是按「听起来危险」排，而是按两个问题排：能不能造成业务影响；从当前权限到影响有几跳。工具和 RAG 排在模型前面，是因为它们天然连接用户输入和内部数据。

2. 信任区域不能只画服务拓扑

传统架构图喜欢按「Web 层、应用层、数据库层」画。AI 目标还要按数据可信度画，否则会漏掉最大的边界：

重点不是 R0 到 R5 的名字，而是跨边界的移动：

数据流 起点 终点 风险问题
用户输入 → 系统提示词拼接 R0 R3 输入能否改变控制语义
外部文档 → 切片 → 检索结果 R0/R1 R3 写入者能否预埋未来触发条件
行情接口返回 → 拼进上下文 R1 R3 第三方字段能否夹带指令
模型输出 → 工具参数 R3 R4 模型能否驱动特权动作
工具结果 → 下一轮上下文 R4 R3 内部返回值是否被二次信任
UAT 配置/数据 → 生产 环境 A 环境 B 弱环境能否影响强环境

3. 这个靶场里的四条边界

  1. 用户输入 → 模型上下文：经典注入点，Sentinel-Guard 在看。
  2. 工具返回值 → 下一轮上下文：如果行情接口的某个字段能被外部影响，这里就是二手注入点。
  3. 知识库文档 → 检索结果：文档来源是研究员上传的晨报 PDF。谁能往知识库写东西，谁就控制了这个入口。
  4. UAT ↔ 生产共享组件：UAT 可达，而 UAT 要测完整功能，大概率连的是和生产同一套知识库。如果共库，UAT 的弱口令就是生产的投毒入口。

第 4 条在普通架构图上经常不存在，在攻击路径上却真实存在。记忆投毒也是同类问题：写入和触发发生在两个边界上，各防一半等于都没防住。

所以呢： 信任边界图不是装饰，它把两个独立的安全问题串成一条攻击路径。单点测试发现不了「UAT 密码策略」和「生产 RAG 投毒」的关系，只有把数据流画出来才会看见。同时，四条数据流就是四个审计埋点：输入拼接、文档入库、工具参数、工具回读。

5. 升级路径规划：三条候选，一条打通

有了边界图，就可以规划路径。规划原则有四个：

  1. 每一步只要求一个新前提。 如果一个动作同时依赖三个未验证假设，它不是路径，是愿望。
  2. 每一步都有可观测信号。 能判断成功、失败或误报，不能只凭「感觉它变了」。
  3. 每一步都预设失败切换。 红队计划不是线性清单，是路径树。
  4. 每一步都受授权和预算约束。 影响生产数据、批量导出、触发外联的动作必须单独确认。

1. 先列完整候选路径，再按成本排序

Step 动作 利用的攻击面 前提 验证信号 失败切换
1 提示注入获取 Agent 控制权 直接注入 对话入口 模型执行偏离原任务 转向业务语义边界输入
1b 顺着业务职责构造边界输入 工具参数注入 Agent 有带参工具 工具收到非预期参数 只做无破坏参数探测
2 通过工具出站请求探测可达性 SSRF / 出站控制 工具可带目标参数 内网服务响应 停止，报告出站面
3 访问云元数据 平台凭证 IMDSv1 或可绕过 凭证 JSON 返回 不继续爆破，改查配置
3b 直连内网向量库 未授权访问 端口可达且无鉴权 集合列表返回 记录可达性，不批量导出
4 用 sources 绘制数据地图 RAG 元数据泄漏 对话权限 文档名和分数返回 控制频次，转防御建议
C UAT 弱口令 → 知识库投毒 → 生产触发 间接注入 UAT 可达 + 共库 生产回答出现投毒内容 仅在授权窗口推演

优先级不是只看严重度，还要看置信度、可回滚性和日志噪音：

路径 业务影响 置信度 可逆性 日志噪音 排序
A：直接注入接管 Agent 高 中 好 中 先试一轮，被拦即切
B：业务参数 → 工具滥用 高 中 好 低 主路径
C：UAT → RAG 投毒 → 生产触发 很高 中 差 高 只推演，实战需额外授权
D：向量库导出还原 高 低 差 高 只确认可达，不批量执行

2. 示例推演：Path A 被拦，然后切到 Path B

推演开始时，直接注入大概率被 Sentinel-Guard 拦下，返回固定话术，和指纹阶段判断一致。黑名单式防护不硬碰，切换到 1b：顺着 Agent 的正常职责构造边界输入。

净值查询是它的本职工作，那就给它一个正常业务里可能存在的输入形态：

模型把请求转给了 quote-tool。工具的实现是：查询净值 → 把结果 POST 到 callback_url。callback_url 没有做目标白名单，服务端按参数原样请求。一个藏在业务参数里的 SSRF 出现了；风控全程没有告警，因为每一轮对话都在正常职责范围内。

假设拿这个 SSRF 尝试云元数据端点，失败。IMDSv2 开着，要求先取 Token，当前请求方式满足不了。这说明靶场在平台层的基础防御配置生效了。但这个请求原点的价值不只在云元数据，它证明应用容器可以触达内网。如果低频验证内网可达性，Milvus 很可能浮出水面：

19530 未授权，集合列表直接返回，而且 wealth_kb_uat 和 wealth_kb_prod 在同一个实例里。UAT 共库从推测变成实锤。向量导出和逆序攻击的前提成立；生产知识库内容存在被还原的可能。

推演到这里必须停住。确认未授权访问是验证漏洞，批量导出生产数据是另一次授权。 示例只记录集合名和可达性，不做导出。

3. Path C 推演：不用执行也能写进报告

一旦确认共库，Path C 的每一步前提都可以被验证：

  1. UAT 入口在靶场边界内可达。
  2. UAT 与生产共享向量库，来自集合列表。
  3. 知识库文档来源是人工上传的 PDF，来自 sources 路径和架构注释。

完整链条可以推演出来：UAT 弱口令或未授权接口 → 登录 knowledge-admin → 上传一份嵌入了间接注入指令的「晨报 PDF」→ 下一次生产用户检索到相关内容 → 指令进上下文 → Agent 执行。投毒一次，所有触发相关检索的会话都可能命中，攻击者不需要保持任何连接。

Path C 默认不做实战化。原因很简单：它会影响生产回答，属于持久化影响，超出了普通演练授权的默认边界。威胁建模要指出这条路径，执行计划要把它隔离成「需安全负责人额外确认」。

quote-tool 的 callback_url 无白名单 高 低，一轮对话 应用容器可触达内网服务 工具参数做目标地址白名单，拒绝内网段和云元数据
Milvus 内网未授权 + UAT/生产共库 严重 中，需先获得 SSRF 知识库内容可枚举，跨环境投毒成为可能 开启鉴权；UAT 与生产实例隔离
sources 泄露内部文档元数据 中 极低 暴露知识库组织结构和检索阈值 sources 只返回引用计数，不返回路径和原始分数
Sentinel-Guard 只覆盖显式注入语义 中 低 攻击者借正常业务动作绕过 增加工具层参数校验和异常外联审计

报告里不要把 SSRF 写成孤立的 HTTP 问题，也不要把 Milvus 写成孤立的数据库问题。业务影响必须落在同一条链上：一个正常业务参数把应用权限转成了内网可达性，内网可达性把 UAT 和生产连成一个信任域，跨环境知识库又把文档上传变成了生产 Agent 的指令入口。

6. 任务分解：把路径树翻译成排期

路径树确认后，最后一步是拆成可执行任务。每个任务至少标注权限、交互预算、证据、止损动作：

任务 所需权限 预算 采集证据 告警/止损动作
指纹探测 公开对话入口 7 轮，分三轮隔开 请求/响应、头字段、行为结论 出现封禁提示立即停 24 小时
RAG 元数据测试 公开对话入口 3-5 轮 sources 字段、路径、分数 命中高频文档即停止枚举
边界输入注入 公开对话入口 1-2 轮 工具调用外联日志 触发风控全局提示立即停止
内网可达性验证 SSRF 可用 10-15 次请求 目标端口/服务指纹 遇生产关键服务只记录不停留
向量库验证 内网可达 只查集合列表 API 响应、权限错误 不批量导出，不还原正文
Path C UAT 账号 默认不执行 前提矩阵和影响推演 安全负责人书面确认后才进入窗口

其中三个约束比「测得多」更重要：

  1. 交互预算：每个入口预先设上限，避免模型策略层或风控把散点请求归并成攻击会话。
  2. 时间窗：涉及工具外联、内网探测、批量读数据的动作放在授权窗口里，不混进业务高峰。
  3. 可回滚性：能留下持久化影响的动作，例如记忆写入、文档入库、账号创建、配置修改，默认只推演。

任务分解的产出不是排期表本身，而是一套可审计的决定：为什么先测 B、为什么暂停 C、为什么导出动作被砍掉。这样即使中途触发告警，安全负责人也能快速理解边界在哪里。

7. 给防御方的自评顺序

这篇写的是红队视角，但防御方的自评流程是同一个。按「一小时能做完」排：

  1. 盘点 AI 相关域名、网关和测试环境。 UAT、网关、向量库、知识库后台经常是资产台账里缺失的那一类。
  2. 对自己的对话入口跑一遍指纹问题。 sources 吐不吐路径、工具参数收不收 URL、限流阈值是多少，十分钟出全部结果。
  3. 填组件映射表。 有几格填不出来？填不出来本身就是风险，说明资产不清。
  4. 画跨边界数据流。 只需回答一个问题：谁能往 RAG 知识库写东西？ 把每一个答案列出来，逐个检查认证、审批和审计。
  5. 检查 UAT 与生产的共享组件。 共用的知识库、网关、向量库实例和配置中心，是 AI 攻击路径里最常见的一条暗边。
  6. 把业务参数里的 SSRF 列入测试用例。 风控防的是提示注入关键词，防不住一个长得像正常需求的 callback_url。工具参数白名单必须做在工具实现层，WAF 永远盖不住。
  7. 审计四个控制点。 输入拼接、文档入库、工具参数、工具结果回读。只记录自然语言输入/输出的日志，看不见真正的转移点。
  8. 为持久化动作设独立审批。 记忆写入、知识库写入、Agent 账号绑定、自动化任务创建，不能和普通聊天同权。

8. 八个常见错误

  1. 把模型当成唯一目标。 模型只是上下文处理器，真正的权限经常在工具、检索和配置里。
  2. 把旧架构图当现网事实。 版本、路由和共享组件必须用证据刷新。
  3. 只测用户输入，不测内容来源。 RAG 文档、工具返回值和历史会话都是延迟到达的输入。
  4. 把防护当成黑盒开关。 不分输入层、策略层、工具层，就无法规划绕过和防御。
  5. 路径没有失败分支。 被拦以后继续堆 payload，只会消耗交互预算。
  6. 把能力误报成影响。 能出站不等于能拿凭证，能读集合不等于已经导出数据。
  7. 没有止损条件。 触发封禁、影响生产数据、产生持久化状态，都应有明确停止动作。
  8. 报告只写漏洞。 安全团队更需要知道控制点在哪里，以及修复后如何复测。

威胁建模的产出不是一份方法论文档，而是几张标了「不可信」的图、一张排好优先级的路径树和一张可审计的排期表。下次遇到 Agent 靶场或真实 AI 系统，先花一小时画边界，再动手打——顺序反过来就是无效功。
